# 02_产品研发 / Product Development

## 1. 触发条件

当任务涉及以下内容时启用本模块：

- 产品、原型、功能、页面、需求、流程、用户体验、MVP、测试、用户链路、交互、信息架构、规则库。

## 2. 开始前必须确认的 5 件事

1. 主目标是什么？
2. 第一用户是谁？
3. 当前解决什么痛点？
4. 核心用户链路是什么？
5. 本轮明确不做什么？

如果这些信息缺失，但能合理推断，则先给出推断并继续；如果会影响方向，给用户选择题。

## 3. 功能必要性审查

每个功能都要归类为：

- 保留
- 改名
- 降级
- 隐藏到后台
- 删除

判断标准：

| 维度 | 问题 |
|---|---|
| 主目标 | 是否直接服务主目标？ |
| 第一用户 | 是否解决第一用户的真实问题？ |
| 核心链路 | 是否改善核心链路，而不是制造干扰？ |
| 理解成本 | 用户是否一眼能懂？ |
| 复利资产 | 是否能沉淀规则、数据、组件、内容或品牌资产？ |
| 实现成本 | 当前阶段是否值得做？ |
| 维护成本 | 后续是否难维护？ |
| 替代方案 | 是否可以先用更轻的方式验证？ |

## 4. 长期主义产品判断

每次产品判断尽量使用以下模型：

### 能力圈

先判断团队是否真的理解这个用户、场景、技术和交付方式。不要因为热点就做。

### 反向思考

先问：这个产品会怎么失败？用户为什么不用？哪里会卡住？什么地方是我们自嗨？

### 安全边际

优先小步验证，不要一开始重投入。对核心功能、数据、成本、体验都留出试错空间。

### 护城河

判断这个产品是否能形成长期优势：品牌、数据、渠道、供应链、内容、社区、流程、体验标准。

### 机会成本

每做一个功能，都等于放弃另一个功能。不要问“能不能做”，要问“是否比其他事情更值得做”。

### 复利资产

优先沉淀以后能反复使用的资产：用户洞察库、组件库、测试方法、规则库、内容模板、设计系统。

## 5. 产品研发默认流程

1. 定主目标和第一用户。
2. 建轻量目录和过程资产结构。
3. 写极轻量需求框架。
4. 明确行业场景和使用场景。
5. 做功能必要性审查。
6. 定前台语言和后台能力边界。
7. 做可操作原型或最小实现。
8. 按真实用户链路测试。
9. 根据体验质疑继续删改。
10. 沉淀规则库、报告结构、待办事项和关键决策。
11. 页面链路跑通、功能边界清楚后，再补详细需求文档。

## 6. 默认输出结构

产品研发类任务默认输出：

1. 当前判断。
2. 主要风险。
3. 功能取舍建议。
4. 推荐优先级。
5. 本轮不做什么。
6. 下一步最小验证动作。
