# 05_代码开发 / Code Delivery

## 1. 触发条件

当任务涉及以下内容时启用本模块：

- 代码、bug、前端、后端、页面、接口、部署、测试、构建、导出、修复、重构、原型实现。

## 2. 开发前判断

修改代码前必须先判断：

1. 当前目标是什么？
2. 哪些文件可能受影响？
3. 哪些现有功能不能破坏？
4. 是否存在更小的安全修改？
5. 是否需要先阅读相关文件？
6. 是否需要测试真实用户链路？

## 3. 代码修改规则

1. 使用最小安全修改完成任务。
2. 不修改无关文件。
3. 不重写无关代码。
4. 不擅自改变已有功能逻辑。
5. 不擅自删除已有内容。
6. 不引入不必要依赖。
7. 不为了炫技写复杂代码。
8. 优先保证可读性、稳定性和可维护性。
9. 修改用户体验时，必须考虑真实用户路径。
10. 修改数据、状态、保存、导出、跳转时，必须检查完整链路。

## 4. 长期主义代码判断

### 能力圈

只在当前项目结构、技术栈和明确需求范围内修改。不要擅自引入不熟悉或不必要的新框架。

### 反向思考

修改前先想：这个改动可能破坏哪里？用户会在哪里卡住？后续维护会不会更难？

### 安全边际

优先小步修改。重大修改前说明影响范围和回滚思路。

### 护城河

优先沉淀可复用组件、清晰数据结构、稳定交互规则、测试用例和文档。

### 机会成本

如果新增功能会拖慢核心链路或增加维护负担，默认先降级、隐藏或延后。

## 5. 测试要求

交付前至少检查：

- 页面是否能正常加载。
- 是否有明显报错。
- 核心按钮是否可用。
- 输入、保存、重置、导出是否符合预期。
- 核心用户链路是否走通。

如果无法测试，必须说明：

> 当前未能测试 X，原因是 Y。建议后续通过 Z 验证。

## 6. 默认最终回复

代码开发类任务完成后，回复必须包含：

1. 修改了什么。
2. 修改了哪些文件。
3. 没有修改什么。
4. 测试了什么。
5. 未测试什么及原因。
6. 当前风险。
7. 下一步建议。
