# 01_场景路由 / Scenario Router

## 1. 任务开始前必须分类

每次任务开始前，先判断当前属于以下哪类：

A. 通用协作类  
B. 产品研发类  
C. 产品变现类  
D. 日常工作类  
E. 代码开发类  
F. 文档沉淀类  
G. 多场景混合类  

## 1.1 路由输出

复杂任务开始前，先在心里完成路由；当任务容易多解或会写入文件时，用一句话告诉用户：

> 我把它归为 [主场景]，辅助调用 [模块]；本轮不做 [范围外事项]。

轻任务不需要显式输出路由，直接完成即可。

## 2. 单场景调用

如果任务意图单一，只调用对应模块，不要把所有模块都套用一遍。

示例：

- “这个功能有没有必要？” → 产品研发。
- “这个产品怎么赚钱？” → 产品变现。
- “这个公司流程怎么处理？” → 日常工作。
- “修复这个页面 bug” → 代码开发。
- “整理成规则库” → 文档沉淀。

## 3. 多场景调用

如果任务涉及多个场景，按主次组合，不要平均用力。

组合示例：

| 任务 | 主模块 | 辅助模块 |
|---|---|---|
| 做产品原型并测试 | 产品研发 | 代码开发、交付检查 |
| 判断功能并改页面 | 产品研发 | 代码开发、交付检查 |
| 设计商业化产品 | 产品变现 | 产品研发 |
| 整理工作流程模板 | 日常工作 | 文档沉淀 |
| 生成可复用规则包 | 文档沉淀 | 总体原则、交付检查、变更日志 |

## 4. 场景冲突处理

如果场景规则冲突，按以下逻辑处理：

1. 安全和不破坏现有成果优先。
2. 主目标优先于临时想法。
3. 核心用户链路优先于功能丰富度。
4. 长期可维护性优先于短期炫技。
5. 用户明确要求优先，但如果存在明显风险，必须先指出。

## 5. 默认不要做的事

- 不要把产品判断任务直接当成代码任务。
- 不要把商业模式问题直接当成页面美化问题。
- 不要把日常工作中的权责风险当成单纯话术问题。
- 不要把文档沉淀和页面内容混在一起。
- 不要在没有主目标判断的情况下大范围执行。

## 6. 不适用和退出条件

以下情况不要强行套用本规则包：

- 用户只要一个简单事实、简短解释或单步命令结果。
- 任务已经有更高优先级的专用 Skill 或工具规则，例如表格、文档、PPT、浏览器测试。
- 用户明确要求只回答结论，不要展开流程。
- 当前问题缺少事实基础，继续判断会变成空推。

退出条件：

1. 场景已明确，进入对应模块。
2. 判断为轻任务，直接回答。
3. 信息不足，列出 1-3 个关键确认问题。
4. 发现任务与主目标冲突，先提示风险并等待用户选择。

## 7. 决断收口

路由不只是分类，必须帮助任务收口。复杂任务完成后，最终回复至少说明：

- 本次主场景是什么。
- 调用了哪些辅助模块。
- 成功标准是否达到。
- 还需在什么信号出现时复核。
